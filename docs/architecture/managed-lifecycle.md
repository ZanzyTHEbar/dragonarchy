# Managed Lifecycle Stability Contract (Active Fleet)

## Retirement priority and session protocol

**Owner directive, clarified 2026-10-23: outcome parity, cohesive replacement and complete legacy retirement take priority over unrelated feature expansion. This gate is OPEN.**

The required order is: supported capability parity → independent managed installation/update/recovery → safe cutover and qualification → complete legacy provisioning removal → final post-deletion qualification → new features. Guarding or deprecating `install.sh` does not satisfy removal. Do not leave a functional legacy recovery installer as the permanent end state.

Parity preserves required outcomes, not every incumbent script, daemon, application choice or implementation detail. The owner explicitly includes the Omarchy reconciliation, corrective refactoring, cruft removal and cohesive desktop orchestration in this work. Quickshell/plugin integration and command, configuration, session, update and recovery improvements may replace patchwork while closing the relevant ledger gaps; they do not require a separate feature-priority override. Do not first port an obsolete implementation merely to replace it again.

Unrelated capabilities, speculative frameworks and additional platform support remain deferred. Preserve unrelated dirty work, including mobile/Wayle/Wleave/theme/OpenCode changes. Working in the same files is not sufficient justification: connect each change to a retained outcome, an ownership/reliability defect or a bounded architectural replacement. A blocked qualification step is not permission to expand scope.

### Resuming and handing off

1. Read root `AGENTS.md`, this contract and its closure ledger; inspect Git status and the relevant implementation. Historical reports are not current evidence.
2. Select the first actionable unclosed gap or a bounded replacement that closes its dependencies. Record the retained outcome, current/replacement owner, affected hosts and recovery boundary in the existing ledger. Required capabilities remain required until the owner retires them; obsolete implementations need not be preserved once their replacement is proven.
3. Apply the five-step sequence proportionally: validate requirements → remove unnecessary scope/duplication → simplify survivors → shorten trustworthy feedback → automate stable repetition. Make the smallest coherent product change, which may replace several duplicate writers rather than patch each one. Run relevant existing checks and, when useful, one focused real-flow acceptance check. Static checks do not establish native readiness.
4. Update the relevant ledger row with exact paths, checks and results, remaining blockers, and the next actionable step. Use existing tasks rather than duplicate trackers. A handoff must leave an obvious next parity action, not a new feature backlog.
5. Keep the feature gate OPEN until every retained capability has a managed owner and acceptance evidence, obsolete legacy execution and CI dependencies are removed, and the final post-deletion revision is qualified across the four active hosts.

This clarification authorizes bounded repository implementation, corrective replacement and removal of proven obsolete source. It does not authorize live operations or destructive target changes. Native qualification remains deferred. Live host/SSH/native-package/VM/apply/service/boot/cutover operations require scoped approval; commits, pushes and PRs require a request. A blocked or deferred required check keeps retirement incomplete.

### Product outcome and architectural direction

Dragonarchy is intended to be a reproducible, opinionated Linux host-management system, not merely a personal dotfiles collection and not necessarily a distribution with its own ISO or repositories. Users should be able to declare supported hosts, select reliable capabilities and personalize defaults without editing core code for each hostname. The four-host fleet below is the mandatory acceptance baseline; it is not the whole product model or proof of general availability.

- **Retain outcomes, evaluate implementations.** Preserve useful shell/editor workflows and required hardware, networking, storage and security behavior. Do not preserve an implementation solely because it is familiar or expensive to replace; do not import an upstream feature solely because it exists.
- **Adopt cohesion deliberately.** A coherent Quickshell-based desktop using suitable Omarchy lifecycle/plugin mechanisms is an approved parity direction, not a commitment to install Omarchy wholesale or to rewrite every component. Establish the selected runtime/helper/provider boundary and recoverable cutover. Do not grow Waybar, a separate Wayle fork and an upstream-derived shell into parallel permanent orchestration platforms.
- **Keep one owner per concern.** Ansible owns system policy/activation; chezmoi owns static user files; runtime components own declared generated state and mutable GUI preferences. Do not make GUI-edited preferences and continuously applied static configuration compete for the same path. A desktop UI must not become a second provisioning engine.
- **Deliver coherent inputs.** Treat selected runtime code, defaults, units, helper APIs and plugin revisions as a compatible release. Declare which inputs are pinned and which track an upstream repository; repeat convergence does not prove repeatable package versions or byte-identical systems. Unknown providers or compatibility stay blocked, not guessed.
- **Qualify the whole fleet.** A replacement desktop is only one part of parity. Both desktop hosts, the server and the local container must retain their required behavior on the final revision, without legacy provisioning or a preseeded home concealing gaps.

The reviewed Omarchy baseline is [v4.0.6 / `237f1b4`](https://github.com/omacom/omarchy/tree/237f1b4071a0bff2296c6d740ba2b9fd695ebfa0). Its [runtime/settings producer recipes](https://github.com/omacom/omarchy-pkgs/tree/7b983a29a327a4cc163e9063b5f6a97c7f6c8dcb/pkgbuilds) declare the same source revision. These are source evidence, not measured fleet reliability or approval to apply upstream package defaults. Detailed temporary inventories are research aids, not a substitute for this ledger or native acceptance.

## Lifecycle Invariants Enforced in Code

1. **Truthful Package Convergence (`infra/ansible/roles/packages`)**:
   - Every group selected by `host_profile_packages` (plus `sddm` when `display_manager == 'sddm'`) is required.
   - `packages_pending_paru_policy` and `packages_pending_script_policy` default to `fail` and reject `report` overrides before resolution or installation.
   - `resolve.yml` validates the full `export-package-plan.sh` JSON schema, group provenance, and flattened manager arrays before `install.yml` runs. Any non-empty `pending.paru` or `pending.script` list from a selected group fails closed before the `packages` role installs a native package. Host-specific opt-in groups are not selected by the active Ansible inventory; adding one makes its provider requirement binding.

2. **Idempotent Time Management and Explicit Collection Dependencies (`infra/ansible/roles/base`, `infra/ansible/requirements.yml`)**:
   - System timezone and NTP state are inspected via `timedatectl show` and mutated via `timedatectl set-timezone` / `timedatectl set-ntp true` only when drifted. This removes the invalid `ansible.builtin.timezone` reference and the unconditional `changed_when: true` churn.
   - `infra/ansible/requirements.yml` declares `community.general` for `community.general.ufw`.

3. **Explicit `UNKNOWN` Platform Facts (`infra/ansible/inventory/group_vars/all.yml`)**:
   - Exact distro release version, CPU architecture, kernel family/version, boot firmware/bootloader, filesystem, encryption, and Secure Boot state remain `UNKNOWN` until collected from target hardware or an approved disposable VM.

## Current Supported Product

The repository currently supports a **fail-closed managed control plane**, not a fleet-ready provisioning claim:

- The canonical `install` must select an inventory host and a non-root user; remote user state is shipped as a manifest-only archive and reconciled on the target. The legacy `install.sh` recovery path is not the managed contract.
- `site.yml` resolves packages from `scripts/install/deps.manifest.toml`; required repo-native tiers install only after the whole plan validates. Non-repo host extras are separate opt-in groups and are not part of the managed required baseline.
- `update.yml` performs targeted package upgrades for the selected host; it does not invent a target.
- Host-level secret, service, and activation ownership remains Ansible; static user files remain chezmoi.

### Known Gaps

1. **Session manifests are scoped; devtools still mix CLI and GUI payloads.** Both sync paths now use inventory `host_desktop_stack`: `none` selects `devtools-core`, `git-ssh`, `session-zsh`; `hyprland` also selects `session-core` and `session-shell`. Missing/unsupported values fail closed. `devtools-core` still includes Kitty, Zed, Alacritty and fcitx5, so headless sources are not entirely GUI-free. Their retained scope needs explicit reconciliation; this patch does not remove them or certify native operation.
2. **No active host has a required pending package tier.** The three non-repo extras are modeled as host-specific opt-in groups not selected by the active Ansible inventory: `libinput-gestures` (`host_firedragon_gestures`), `gum` (`host_debian_installer_ui`), and `gh` (`host_ubuntu_mobile_dev_github_cli`). Adding one to `host_profile_packages` deliberately makes its provider requirement binding; no provider URL, version, or installer should be guessed. The legacy `install-deps.sh` still installs these host-specific groups on their matching hosts, while the managed Ansible path does not. `--user-only` and `--update` do not run the package gate and report only their own scoped completion.
3. **Native qualification is deferred.** Static parsing, isolated Ansible task evaluation, and shell tests do not prove kernel, package availability, display-manager, bootloader, container, or hardware behavior on the targets.
